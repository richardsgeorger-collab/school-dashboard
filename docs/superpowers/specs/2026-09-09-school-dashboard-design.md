# School Dashboard — Design Spec

Date: 2026-09-09
Owner: George Richards (freshman BSME, Grand Canyon University, Fall 2026)
Status: Approved

## 1. Purpose

A mobile-friendly web app that turns GCU syllabus PDFs into a single plan:
every assignment, quiz, exam, lab, and project with its due date, a realistic
time estimate, and a computed "start by" date; a calendar; a dashboard of what
is due and what to start today; a workload heatmap; and a points-based grade
tracker. Data syncs across phone and laptop through Supabase, with browser
storage as an always-on local cache and fallback.

## 2. Decisions already made

| Decision | Choice |
|---|---|
| Frontend | Vite + React 18 + TypeScript, plain CSS with custom properties |
| Backend | Supabase (Postgres + Auth, email/password). Local-first; Supabase optional |
| Hosting | GitHub Pages, repo `school-dashboard`, deployed by GitHub Actions |
| Time zone | `America/Phoenix` (UTC-7, no DST). Stored in settings |
| Capacity defaults | 3 h per weekday, 5 h per weekend day of schoolwork outside class |
| Participation items | Graded participation/DQ items are included; 0-point items excluded from seed (importer has a toggle) |
| Syllabus import | In-app PDF importer (pdf.js) using the same parser that generates the seed |
| Grades | Points-based (earned / possible). Syllabi publish no category weights |
| Class meetings | CHM-113 W/F 7:00–8:15 AM; CHM-113L Mon 6:00–8:50 PM (PM assumed); ENG-105 W/F 11:00 AM–12:45 PM; ESG-162 T/Th 7:00–8:15 AM; ESG-162L Tue 12:30–2:20 PM; UNV-106 online (no meetings) |

## 3. Architecture

```
src/
  main.tsx, App.tsx            # shell, routing between views (hash router)
  domain/
    types.ts                   # Course, Item, Settings, Term
    estimate.ts                # rule-based time estimator
    schedule.ts                # capacity-aware start-by scheduler + risk flags
    dates.ts                   # tz helpers (Phoenix-local calendar dates)
    classify.ts                # item type from title/course
  parser/
    gcuSyllabus.ts             # text -> {course, items[]}
    pdfText.ts                 # pdf.js -> lines (browser + node script)
  storage/
    repository.ts              # Repository interface
    localRepo.ts               # localStorage implementation
    supabaseRepo.ts            # Supabase implementation + sync
    store.ts                   # app state (React context/reducer), persistence, recompute
  views/
    Dashboard.tsx, Calendar/ (Month, Week, Agenda), Heatmap.tsx, Grades.tsx, Settings.tsx
    ItemDetail.tsx (modal), ImportSyllabus.tsx
  data/seed.json               # generated by scripts/seed.ts from syllabi/*.pdf
scripts/seed.ts                # node: parse PDFs -> src/data/seed.json
supabase/schema.sql            # tables + RLS, pasted into SQL editor
.github/workflows/deploy.yml   # build + deploy to Pages
```

Units and their contracts:

- **parser/gcuSyllabus** — `parseGcuSyllabus(lines: string[]): ParsedSyllabus`.
  Pure. Depends on nothing. Tested with fixtures taken from the real syllabi.
- **parser/pdfText** — `extractLines(pdfBytes): Promise<string[]>`. Wraps
  pdfjs-dist; groups text items by y-position into lines; strips GCU page
  footers ("Page N Grand Canyon University 2026 © Prepared on: …") and the
  timestamp header line.
- **domain/classify** — `classifyItem(title, courseCode): ItemType`. Pure.
- **domain/estimate** — `estimateMinutes(item, course): number`. Pure, rule table.
- **domain/schedule** — `computeSchedule(items, courses, settings, today)`
  returns per-item `{startBy, risk, plannedMinutesByDay}` and per-day load.
  Pure.
- **storage/repository** — `load(): Promise<AppData>`, `saveCourse`, `saveItem`,
  `deleteItem`, `saveSettings`. Both implementations conform; `store.ts` writes
  to local always and to Supabase when connected.

## 4. Data model

```ts
type ItemType = 'exam'|'quiz'|'homework'|'lab'|'paper'|'project'|'discussion'|'participation'|'other';
type ItemStatus = 'todo'|'in_progress'|'done';

interface Meeting { day: 0|1|2|3|4|5|6; start: string /*HH:mm*/; end: string; location?: string }

interface Course {
  id: string; code: string; name: string; color: string; credits: number;
  instructors: {name: string; email: string}[];
  meetings: Meeting[]; online: boolean;
  termStart: string /*YYYY-MM-DD*/; termEnd: string;
  updatedAt: string;
}

interface Item {
  id: string; courseId: string; title: string; type: ItemType;
  points: number; opensAt: string | null; dueAt: string;   // ISO with offset
  estimatedMinutes: number; estimateOverridden: boolean;
  startByOverride: string | null;                          // YYYY-MM-DD
  status: ItemStatus; completedAt: string | null; score: number | null;
  notes: string; topic: string | null;
  flags: { inClass: boolean; group: boolean; lopesWrite: boolean; timed: boolean; practice: boolean };
  source: 'parsed'|'manual'; updatedAt: string;
}

interface Settings {
  timezone: string; weekdayMinutes: number; weekendMinutes: number;
  theme: 'system'|'light'|'dark'; weekStartsOn: 0|1;
  supabaseUrl: string | null; supabaseAnonKey: string | null;
  updatedAt: string;
}
```

Derived (never stored): `startBy`, `risk`, per-day planned minutes, weekly
load, grade summaries.

## 5. Parser rules (GCU syllabus format)

Input is the ordered list of text lines from all pages, footers removed.

1. Course header: the line matching `^([A-Z]{2,4}-\d{3}[A-Z]?)\s+(\d+) Credits?\s+(\w{3} \d{1,2}) - (\w{3} \d{1,2})$`
   gives code, credits, term start/end (year from the prepared-on date). The
   line before it is the course name.
2. Instructors: lines between `Instructor Contact Information` and
   `Class Resources`; pairs of name line + email line.
3. Topics: `^Topic (\d+): (.+)$` followed by `^(\w{3} \d{1,2}, \d{4}) - (\w{3} \d{1,2}, \d{4})\s+Max Points: (\d+)$`.
   Current topic is attached to subsequent items.
4. Assessment: a header line `Start Date & Time Due Date & Time Points( Time Limit)?`
   The item title is the nearest preceding non-empty line. The next line matches
   `^(\w{3} \d{1,2}, \d{4}, \d{1,2}:\d{2} [AP]M)\s+(\w{3} \d{1,2}, \d{4}, \d{1,2}:\d{2} [AP]M)\s+(\d+)(\s+(.+))?$`
   giving opensAt, dueAt, points, optional time limit.
5. Traits: after `Assessment Traits`, lines until `Assessment Description` or the
   next title: `Timed`, `Group`, `Requires LopesWrite`, `Not Submitted in Halo`,
   `Benchmark`. `Not Submitted in Halo` + due time earlier than 11:59 PM ⇒ inClass.
   Any due time before 11:59 PM on a meeting day ⇒ inClass.
6. Description: lines after `Assessment Description` until the next assessment
   title/header or Topic. Stored as notes (trimmed to 600 chars).
7. Practice flag: title contains "Practice".

Dates are interpreted in the settings time zone and stored as ISO strings with
the `-07:00` offset.

## 6. Classification and estimates

Classification (first match wins, on lowercase title; course code ending in L
biases toward lab):
exam → `exam`; quiz (incl. practice, APA) → `quiz`; `dq` → `discussion`;
`participation` → `participation`; lab / practical → `lab`; clc / design report /
demo → `project`; essay / report / draft / presentation / op-ed / review
assignment / reflection / analysis → `paper`; homework / activity / review /
matlab / excel / zybooks / aleks / plan / installation → `homework`; else `other`.

Estimate table (minutes; then editable per item):

| exam | 360 + points × 1.8 (Exam 1 = 630, Exam 2 = 720) |
| quiz, in-class, ≥40 pts | 180 |
| quiz, practice | 90 |
| quiz, other (APA, UNV topic quizzes) | 60 |
| homework, ALEKS course (CHM) | 120 (Topic Activity 90) |
| homework, "Topic N Review" (zyBooks) | 120 |
| homework, ESG "Topic N Homework" | 180 |
| homework, MATLAB / Excel | 180 |
| homework, other | 60 + points × 1.5, capped 240 |
| lab (CHM-113L notebook lab) | 150 |

## 7. Scheduler

Inputs: open items (status ≠ done), settings capacity, today (Phoenix date).

1. Build a day → capacity map from term start to term end: weekday
   `weekdayMinutes`, weekend `weekendMinutes`.
2. Effective deadline day: the Phoenix date of `dueAt`; if due time is before
   6:00 PM, use the previous day.
3. Process items sorted by effective deadline descending, ties by points
   descending. For each, walk backward from the deadline day, allocating
   `min(remaining, freeCapacity(day))` per day, never before `opensAt` date and
   never before today. Record the earliest day allocated as `latestStart`.
4. `startBy = latestStart − buffer`, buffer = 0 days for ≤ 45 min, 1 day for
   ≤ 4 h, 2 days otherwise, floored at `opensAt`. Manual override wins.
5. Risk flags: `overdue` (past due, not done); `at_risk` (could not allocate
   all minutes before the deadline, or startBy < today and status is todo);
   `due_soon` (due within 48 h); `start_today` (startBy ≤ today, not started).
6. Items ≤ 45 min skip allocation and get `startBy = deadline − 1 day`.

Output also includes planned minutes per day per item (used by the week view
and heatmap) and total load per ISO week per course.

## 8. Views

- **Dashboard** (default): status strip (overdue, at-risk, due this week,
  hours needed this week vs capacity); Reminders panel; "Start today"; "Due this
  week" grouped by day; per-course hours-this-week bars. Every item row has a
  complete checkbox and opens ItemDetail.
- **Calendar**: month / week / agenda segmented toggle. Month: chips (dots on
  narrow screens, tap day → day list). Week: time grid with class meeting
  blocks, due items pinned at the top of each day, faint "planned work" bars.
  Agenda: chronological groups by day, from today. Course filter chips.
- **Heatmap**: rows = courses (+ total), columns = semester weeks, cell shade =
  planned hours; total row colored against capacity; hover/tap shows items.
- **Grades**: per course: earned / possible-graded, percentage, remaining
  points, projected final if remaining scored at current average.
- **Settings**: courses (name, color, meetings editor), capacity, week start,
  theme, Supabase connect (URL + anon key, sign up / sign in / sign out, sync
  status), Import syllabus (drop zone, preview table with include toggles,
  0-point toggle), Export/Import JSON, Reset to seed, Add item manually.
- **ItemDetail** modal: all editable fields, mark done with optional score,
  start-by override, delete.

Visual direction: a single strong accent, course colors as the only other
hue family, generous type scale, dark and light themes via `prefers-color-scheme`
and manual toggle. Minimum tap target 44 px. No horizontal page scroll.

## 9. Storage and sync

- `LocalRepo`: single key `school-dashboard:v1` holding `{courses, items, settings}`.
- `SupabaseRepo`: tables `courses`, `items`, `settings`, columns
  `id uuid pk, user_id uuid not null default auth.uid(), data jsonb, updated_at timestamptz`.
  RLS: `user_id = auth.uid()` for all operations.
- `store.ts`: loads local first (instant render). If Supabase configured and
  session exists: pull all rows, merge by `updatedAt` (newest wins), push any
  local rows newer than remote, persist merged to local. Every write goes to
  local immediately and to Supabase in the background; failures are queued in
  local and retried on next sync. Pull again on `visibilitychange` → visible.
- Supabase URL/key come from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` at
  build time, overridable in Settings (stored locally only).
- First run with empty local and no remote data loads `seed.json`.

## 10. Seed generation

`npm run seed` reads every `syllabi/*.pdf`, runs `extractLines` (pdfjs in
Node) + `parseGcuSyllabus`, applies classification, estimates, meeting
defaults and colors from `scripts/courseDefaults.ts`, drops 0-point items, and
writes `src/data/seed.json`. The output is reviewed against the syllabi and
committed.

## 11. Testing

Vitest. Pure modules get unit tests first (TDD): parser fixtures for each of
the 6 syllabi (line arrays captured from the real PDFs), classification table,
estimate table, scheduler scenarios (capacity overflow, opensAt floor, done
items freeing capacity, 8 AM due → previous day), tz date helpers, and the
local/remote merge. Views are checked in the browser via the dev server.

## 12. Deploy

`vite.config.ts` `base: '/school-dashboard/'`. Workflow: on push to `main`,
`npm ci`, `npm test`, `npm run build`, upload `dist`, deploy to Pages. Repo
created with `gh repo create school-dashboard --public`. Pages source set to
GitHub Actions. Web manifest with icons for home-screen install.

## 13. Out of scope

Push notifications, service worker/offline caching beyond localStorage,
multi-user sharing, weighted grade categories, natural-language import of
non-GCU syllabi.

## 14. Implementation notes (deviations from §7)

- Allocation targets `deadline − buffer` (1 day ≤ 4 h, else 2 days) and spills forward into the buffer days only when the buffered window is too small. `startBy` is the first allocated day; no separate subtraction.
- Items whose open date is a real window (opens at least one day before due) are scheduled before unconstrained items, so later big items cannot starve them. An open date on the due day itself (in-class quizzes, lab notebooks) is ignored for scheduling.
- Deletions sync as tombstones (`deleted_at`) so devices converge; the Supabase tables carry that column.
- Course colors were validated with the dataviz palette checker for both surfaces; dark mode uses a separate validated set (`DARK_VARIANT`).
